Critical Logic By Layer

Backend: endpoint rules

applyEndpointPricingRules

This function is the backend hinge. It receives a DB executor, tenant id, endpoint lineage/method, and rules. It refuses to write rules unless the endpoint has OpenAPI lineage.

  • Uses openapi_source_paths to find spec paths.
  • Uses methodCandidates to expand ANY.
  • Writes rules with setPricingRules.
  • Validates through validateOperationPricingRules.
  • Saves the updated spec back as JSON.

Atomic create/update

Endpoint POST and PUT now wrap pricing-rule writes and endpoint row writes in the same transaction. That prevents a half-state where rules are saved but the endpoint is not, or vice versa.

  • POST uses incoming openapi_source_paths.
  • PUT falls back to existing endpoint lineage/method.
  • Both return pricing errors before writing endpoint state.

Read endpoint rules

GET /:id/pricing-rules now returns effective rules, not only operation-local rules. That means root/path inherited rules can show up in the editor.

  • Orphan endpoint returns editable: false.
  • No spec returns editable: false.
  • Valid operation returns rules and method/source metadata.
Backend: tenant/root rules

GET /:id/pricing-rules

Reads root pricing from tenants.openapi_spec. This is default Flex pricing, not endpoint-specific pricing.

PUT /:id/pricing-rules

Parses existing spec or creates a minimal OpenAPI document with createOpenApiSpec, writes root rules, validates, saves JSON, then syncs assigned nodes.

Create tenant with rules

Admin/org create flows can accept pricing_rules. They create a root-pricing OpenAPI spec and validate it before inserting tenant state.

OpenAPI import

Validation got stricter

Import now checks body.spec is a record before validating OpenAPI fields. This avoids treating non-object input as an OpenAPI object.

Root pricing preservation

If the existing tenant spec has root x-faremeter-pricing and the incoming spec does not, import copies the existing root pricing into the incoming spec.

Critical invariant

Importing OpenAPI should update paths and endpoint lineage without silently deleting default Flex pricing. Tests should cover this because it is easy to regress.

Runtime generation

Imported pricing precedence

getImportedOperationPricingRules checks operation, then path item, then root pricing. That matches OpenAPI/Faremeter inheritance: nearest pricing wins.

operationKeyToScheme

Each generated operation gets a scheme. Imported rules with authorize imply Flex. Otherwise the endpoint or tenant default scheme is used.

Capabilities in sync

buildNodeConfig derives advertised schemes from operationKeyToScheme. Without this, mixed tenants can advertise the wrong payment capability to the sidecar.

Frontend state

Friendly vs technical rules

The UI has a friendly rule model with match mode, amount mode, charge timing, hold amount, fields, and fallbacks. It builds the technical rule object used by Faremeter.

Charge timing

upfront means no authorize expression. after-response adds authorize as the maximum upfront hold and capture as final charge.

Technical JSON

Advanced users can edit raw pricing JSON. When technical JSON is dirty, save uses parsed JSON instead of generated friendly-rule output.

Data Flow From UI To Runtime

Form fields

User sets match, charge amount, upfront/after-response, fields, fallback values.

buildRule

Friendly state becomes { match, capture, authorize? }.

Create/Edit payload

UI sends pricing_rules only for Flex and only when rules are relevant.

Endpoint or tenant route

Endpoint rules write operations. Tenant rules write root OpenAPI.

tenants.openapi_spec

Rules live in OpenAPI x-faremeter-pricing.rules.

Gateway spec builder

Runtime spec is built with inherited pricing and operation scheme mapping.

Sidecar config

Sync pushes capabilities and generated spec to the node runtime.

Critical Invariants

  • Endpoint-level pricing rules require openapi_source_paths. If a row is orphaned, the UI must not pretend operation rules can be edited.
  • Saving endpoint rules must update tenants.openapi_spec and endpoint state consistently. That is why POST/PUT use a DB transaction.
  • Root/default Flex pricing and endpoint Flex pricing are different write targets. Root rules go on the OpenAPI document; endpoint rules go on operations.
  • OpenAPI import must preserve existing root pricing unless the new spec explicitly brings its own root pricing.
  • Runtime scheme capability must be operation-derived for mixed Exact/Flex tenants. Tenant default alone is not enough.

What To Ignore On First Read

Do not start with the large table files. They look huge because they add entry points, badges, and modal wiring across dashboard/admin/org surfaces. They are not the conceptual core. First understand schemas, backend rule writes, OpenAPI storage, runtime generation, and frontend rule conversion. Then the UI table changes become easy to classify: fixed-price rows keep inline price editing; Flex rows open a full pricing editor because a scheme toggle alone is not enough data.
